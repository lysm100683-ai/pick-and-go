# How: 프론트엔드용 개발 플랫폼 선택 이유 (2차 중간보고서 수정본)

> ⚠️ 1차 보고서와 달라진 점: Streamlit(프로토타입) → **Next.js(정식 프론트엔드)**로 전환 반영

---

## 요구 성능 (공통)

빠른 프로토타입 검증 후 실제 사용자 대면 서비스 수준의 UI/UX,  
SEO 최적화 및 배포 품질을 갖춘 웹 프론트엔드를 구축해야 한다.

---

## 비교표: 프론트엔드 프레임워크 / 라이브러리 선택

|          | ✅ **Next.js**                                | Streamlit                               | Plotly Dash                        |
|----------|----------------------------------------------|-----------------------------------------|------------------------------------|
| **분류** | **프레임워크** (React 기반 풀스택 웹 프레임워크) | 라이브러리 (Python 데이터 UI 도구)       | 라이브러리 (Python 대시보드 도구)  |
| **이미지** | ▲ Next.js (React)                           | 🟣 Streamlit                            | 📊 Plotly Dash                     |
| **특성** | React 위에서 라우팅·SSR·빌드·배포까지 구조 전체를 제공하는 풀스택 프레임워크. TypeScript 지원. | 데이터 과학 UI에 최적화된 Python 스크립트 기반 동작. 프로토타이핑에 특화. | Plotly 라이브러리 기반의 대시보드 구축 도구. |
| **장점** | • 컴포넌트 기반 SPA 구현으로 정교한 UX 가능<br>• SSR/SSG로 SEO 및 성능 최적화<br>• TypeScript로 타입 안전성 확보<br>• Vercel 배포와 완벽한 통합<br>• 실제 상용 서비스 수준의 UI 구현 가능 | • 사용자 입력 폼과 지도 시각화 등 복잡한 UI를 매우 빠르고 간결하게 구현<br>• Python 코드 몇 줄로 즉시 결과 확인 가능 | • 데이터 시각화에 강력<br>• Python만으로 프론트엔드 구축 가능 |
| **단점** | • Python 백엔드와 연동 시 API 통신 로직 및 별도 개발 필요<br>• 학습 곡선 존재 | • 복잡하고 정교한 웹 표준 UI 구현에 한계<br>• 실제 배포 서비스로는 품질 제한 | • 커스터마이징 자유도가 Streamlit보다 낮음 |
| **선택 이유** | • **1차 프로토타입(Streamlit) 검증 완료** 후, 실제 사용자 서비스 품질 달성을 위해 전환<br>• Vercel 배포와 원클릭 연동으로 CI/CD 구현<br>• FastAPI 백엔드와 REST API로 명확하게 분리된 구조 | (1차 프로토타입 단계에서 사용 후 역할 종료) | |

## 참고: 기술 분류 기준 (용어 정리)

| 용어 | 정의 | Pick & Go 예시 |
|---|---|---|
| **함수 (Function)** | 특정 동작을 수행하는 코드 단위 | `haversine_distance()`, `asyncio.gather()` |
| **라이브러리 (Library)** | 내가 필요할 때 꺼내 쓰는 기능 모음 | React, Pydantic, Streamlit, SQLAlchemy |
| **프레임워크 (Framework)** | 내가 그 안에서 정해진 규칙대로 개발하는 구조적 틀 | **Next.js**, FastAPI, Django |
| **플랫폼 (Platform)** | 소프트웨어가 실행되는 기반 환경 | Supabase, Vercel, Render, Docker |

> **Next.js = 프레임워크**  
> React(라이브러리) 위에서 라우팅, SSR, 빌드, 배포까지 구조 전체를 제공하므로, 사용자가 그 틀 안에서 개발하는 **프레임워크**로 분류합니다.
