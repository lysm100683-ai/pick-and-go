# How: 서비스 배포 플랫폼 선택 이유 

> **핵심 전략**: 프론트엔드와 백엔드를 통합 서버에 올리지 않고, 각 언어/프레임워크 환경에 완벽히 최적화된 2개의 PaaS(Platform as a Service) 플랫폼을 나누어 사용하는 **마이크로서비스형 배포 전략** 채택.

---

## 1. 프론트엔드 (Next.js) 배포 플랫폼 비교표

### 📌 프론트엔드 배포 요구사항
1. **Next.js 호환성**: 프레임워크 코어 기능(SSR 등)이 100% 동작할 것.
2. **응답 속도 최적화**: 글로벌 CDN 탑재로 페이지/리소스 로딩 속도를 극대화할 것.
3. **완전 자동화 (CI/CD)**: 복잡한 구조 없이 소스코드 푸시 즉시 자동 배포될 것.

| | ✅ **Vercel** | Netlify | AWS Amplify |
|---|---|---|---|
| **이미지** | (Vercel 로고 삽입) | (Netlify 로고 삽입) | (AWS Amplify 로고 삽입) |
| **특성** | Next.js의 개발사에서 직접 운영하는 호스팅 최적화 환경 | 정적 웹사이트 및 서버리스 프론트엔드 배포 플랫폼 | AWS 기반의 풀스택 웹/모바일 앱 배포 플랫폼 |
| **장점** | • **Next.js 완벽 호환**: SSR, App Router 등 별도 설정 없이 100% 즉시 동작<br>• 글로벌 Edge Network CDN 기본 제공 (초고속 로딩)<br>• GitHub 푸시 시 자동 배포(CI/CD) 지원 | • 손쉬운 설정과 빠른 빌드 속도<br>• 정적 사이트(SSG) 호스팅에 강력함 | • AWS 생태계(S3, Cognito 등)와 연동 용이<br>• 서버리스 백엔드까지 확장 가능 |
| **단점** | • 백엔드(DB, Python 서버 등) 구동은 사실상 불가<br>• 엔터프라이즈급 트래픽 초과 시 과금 폭이 큼 | • Next.js의 최신 기능(SSR 등) 커버 속도 및 호환성이 Vercel보다 떨어짐 | • AWS 특유의 복잡한 설정 및 권한(IAM) 처리 등 학습 곡선 존재<br>• 소규모 프로젝트에는 무거움 |
| **선택 이유**| **[최종 선택]**<br>Next.js 프론트엔드를 구축하는 데 있어 개발사인 Vercel보다 호환성과 성능이 뛰어난 환경이 없으므로, 설정 비용 'Zero' 달성을 위해 프론트엔드 전담으로 활용. | | |

## 2. 백엔드 (FastAPI) 배포 플랫폼 비교표

### 📌 백엔드 배포 요구사항
1. **컨테이너 환경 지원**: Python 환경과 필수 패키지를 원클릭으로 가상화하여 서빙할 것.
2. **독립적 API 운영**: 프론트엔드와 분리되어 백엔드 복합 연산 로직에만 자원을 집중할 것.
3. **Serverless 편의성**: 보안, 권한, HTTPS 인증 등 별도 인프라 관리 요소가 없을 것.

| | ✅ **Render.com** | Heroku | AWS EC2 (자체 구축) |
|---|---|---|---|
| **이미지** | (Render 로고 삽입) | (Heroku 로고 삽입) | (AWS EC2 로고 삽입) |
| **특성** | Docker 및 웹 서비스 호스팅에 특화된 차세대 모던 클라우드 PaaS | 개발자 친화적인 전통의 클라우드 플랫폼 (PaaS) | 빈 Linux 가상 서버를 대여받아 직접 모든 것을 구축하는 IaaS |
| **장점** | • **Python(FastAPI) 및 Docker 컨테이너 원클릭 배포** 지원<br>• 인프라 관리(OS, 보안, Nginx) 불필요<br>• 포트 개방 및 HTTPS(SSL) 인증서 자동 발급<br>• 저렴한 요금제 및 무료 티어 유지 | • 방대한 애드온(Add-on) 생태계<br>• 직관적인 CLI 및 대시보드 조작<br>• 과거 쌓인 레퍼런스와 튜토리얼이 매우 풍부함 | • **무한한 자유도**: 프론트/백/DB 모두 1개 서버에 구축 가능<br>• 엔터프라이즈급 안정성 및 스케일업 가능성 |
| **단점** | • 한국(서울) 리전 부재 (미국/싱가포르 사용에 따른 약 50ms 지연시간 존재)<br>• 무료 티어 완전 미사용 시 수면(Cold Start) 대기 시간 발생 | • 무료 티어 시스템 완전 폐지로 인한 개발 초기 비용 부담<br>• 대규모 서비스 전환 시 비용이 가파르게 통제 불능으로 상승함 | • Linux 콘솔 조작, 방화벽 방어, Nginx 리버스 프록시 스크립팅 등 **인프라 학습 비용 과다** |
| **선택 이유**| **[최종 선택]**<br>Python 서버 구동을 위해 직접 Linux를 관리해야 하는 AWS EC2의 번거로움을 피하고, GitHub 연결만으로 즉각 Python API 서버가 배포되므로 백엔드 전담으로 활용. | | |

## 결론 및 2차 중간보고서 기재 포인트

Pick & Go 팀은 AWS EC2 기반의 단일 서버 환경 구축이라는 전통적인 모놀리식(Monolithic) 방식을 배제하고, **Vercel(프론트 전용) + Render(백엔드 전용)** 조합을 선택했습니다. 

이는 단순히 셋업의 편의성을 넘어서, **(1) 프론트엔드는 글로벌 CDN(Vercel)으로 클라이언트의 페이지 로딩 속도를 극대화**하고, **(2) 알고리즘 연산이 무거운 백엔드는 독립된 환경(Render)에서 안정적으로 API를 서빙**하도록 설계한 고도화된 마이크로서비스형 아키텍처입니다.
