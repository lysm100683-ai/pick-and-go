# 제 6 장 분산 환경을 위한 예약 파이프라인 설계

본 장에서는 다수의 외부 마이크로서비스(항공, 숙박 등)와 연동하는 환경에서 데이터 정합성을 보장하기 위해 설계된 **Saga 패턴 기반 예약 파이프라인 아키텍처**를 기술한다. 외부 API 통신의 특수성으로 인한 분산 트랜잭션 문제를 분석하고(6.1절), 이를 5단계(Sub 1 ~ Sub 5)의 서브시스템으로 분리하여 해결한 구조(6.2절)와 장애 발생 시의 보상 트랜잭션(Compensating Transaction) 매커니즘(6.3절)을 상세히 다룬다.

---

## 6.1 외부 API 연동의 한계와 Saga 패턴 도입

일반적인 모놀리식(Monolithic) 시스템에서 트랜잭션 관리는 단일 데이터베이스의 ACID 특성에 의존하여 '모두 성공(Commit)'하거나 '모두 실패(Rollback)'하는 원자성(Atomicity)을 쉽게 달성할 수 있다. 그러나 Pick & Go의 예약 시스템은 Amadeus(항공), Booking.com(숙소) 등 외부 벤더의 API에 직접 의존한다. 

외부 API 호출은 데이터베이스의 잠금(Lock) 범위 바깥에서 수행되므로, 숙소 예약은 성공했지만 후행된 항공 예약이 통신 장애로 실패할 경우, 사용자는 '부분 성공(Partial Failure)'이라는 치명적인 상태에 놓이게 된다. 이를 해결하기 위한 전통적인 분산 트랜잭션 기법인 2단계 커밋(2-Phase Commit, 2PC)은 외부 벤더가 프로토콜을 지원해야만 가능하며, 응답을 대기하는 동안 자원 점유가 발생하여 클라우드 환경에서 극심한 성능 저하를 유발한다.[2]

이러한 제약을 극복하기 위해 본 시스템은 **Saga 패턴(Saga Pattern)**을 도입하였다. Saga 패턴은 긴 하나의 복합 트랜잭션을 일련의 로컬 트랜잭션들로 쪼개어 순차적으로 실행하되, 특정 단계에서 오류가 발생하면 이전까지 성공했던 작업들을 논리적으로 취소하는 **보상 트랜잭션(Compensating Transaction)**을 역순으로 실행하여 최종적인 데이터 무결성을 보장한다.[4]

## 6.2 5단계 예약 파이프라인 (Sub 1 ~ Sub 5) 설계

복잡한 예약 도메인의 결합도를 낮추고 각 단계의 단일 책임 원칙(SRP)을 고수하기 위해, 전체 예약 과정을 5단계의 독립적인 파이프라인 모듈로 세분화하였다.

**[표 10]** 예약 파이프라인 5단계 서브시스템 역할 정의

| 모듈명 | 주요 역할 | 시간 복잡도 / 성격 | 실패 시 조치 |
|---|---|---|---|
| **Sub 1. 예약 검증부** | 입력 데이터의 스키마 및 비즈니스 규칙 검증 | O(1), CPU 연산 | 파이프라인 진입 차단 및 클라이언트 반환 |
| **Sub 2. 외부 예약 연동 관리부** | 외부 항공 및 숙박 API 병렬 예약 (Saga 코어) | 네트워크 I/O 병목 | **보상 트랜잭션(취소 API)** 즉시 발동 |
| **Sub 3. 예약 확정 검증부** | 외부 예약 성공 내역을 취합하여 시스템 식별자 발급 | O(1), 메모리 연산 | Sub 2로 롤백 시그널 전파 |
| **Sub 4. 예약 정보 저장부** | 예약 확정 내역을 PostgreSQL 데이터베이스에 영속화 | 디스크 I/O 트랜잭션 | Sub 2로 롤백 시그널 전파 및 DB 롤백 |
| **Sub 5. 예약 결과 안내부** | 비동기 메시지 큐를 통한 이메일/푸시 알림 전송 | 백그라운드 I/O | (알림 실패 시 재시도 큐 적재, 본 트랜잭션 무관) |

### Sub 1: 예약 검증부 (Validator)
사용자로부터 전달받은 JSON 형태의 예약 요청 페이로드를 Pydantic 모델을 통해 1차 검증한다. 날짜의 선후 관계, 탑승객 수와 여권 정보의 일치 여부 등 비즈니스 제약 조건을 이 단계에서 완벽히 필터링하여, 불필요한 외부 API 호출로 인한 자원 낭비와 에러를 사전에 차단한다.

### Sub 2: 외부 예약 연동 관리부 (Parallel Booking)
이 파이프라인의 핵심부로, Python의 `asyncio.gather`를 활용해 독립적인 외부 예약 API들을 **비동기 병렬(Asynchronous Parallel)**로 호출한다. 순차 호출 시 A API(3초) + B API(4초) = 7초가 소요되는 반면, 병렬 호출 시 Max(3초, 4초) = 4초로 응답 시간을 단축한다. 
만약 병렬 실행 중 어느 하나라도 `HTTP 5xx` 에러나 타임아웃을 반환하면, Sub 2는 즉시 실패를 선언하고 이미 성공 응답을 받은 다른 외부 서비스에 대해 `CANCEL` API를 비동기로 전송하는 보상 트랜잭션을 발동시킨다.

[코드 6] Sub 2 파이프라인의 비동기 병렬 예약 및 보상 트랜잭션 로직
```python
async def execute_parallel_booking(flight_req, hotel_req):
    try:
        # 항공과 숙소 API 동시 호출 (병렬 I/O 대기)
        flight_res, hotel_res = await asyncio.gather(
            book_flight_api(flight_req),
            book_hotel_api(hotel_req)
        )
        return flight_res, hotel_res
    except BookingException as e:
        # 실패 시 보상 트랜잭션 발동 (이미 성공한 예약 자동 취소)
        await trigger_compensating_transactions(e.successful_bookings)
        raise SagaRollbackException("부분 예약 실패로 인한 보상 트랜잭션 완료")
```

### Sub 3 ~ Sub 5: 예약 확정 검증, 정보 저장 및 결과 안내
Sub 2를 무사히 통과한 데이터는 Sub 3에서 최종 `Reservation ID`를 부여받고 인메모리 상에서 확정된다. 이어 Sub 4에서는 SQLAlchemy를 통해 PostgreSQL에 영속적(Persistent)으로 커밋된다. 만약 Sub 4의 DB 단에서 Deadlock이나 무결성 제약 조건 위배로 커밋이 실패할 경우, 시스템은 에러를 상위로 전파하여 Sub 2의 보상 트랜잭션을 역으로 트리거함으로써, 방금 전 성공했던 외부 예약들까지 모두 원상 복구시킨다. 

DB 커밋까지 무사히 완료되면 데이터베이스 트랜잭션은 종료되며, Sub 5 모듈이 비동기 백그라운드 워커를 통해 사용자에게 최종 확정 이메일을 발송하며 전체 파이프라인이 종료된다.

## 6.3 장애 복구 및 데이터 무결성 보장

이러한 5단계 파이프라인과 Saga 패턴의 결합은 시스템의 강건성(Robustness)을 비약적으로 끌어올린다. 

어느 단계에서 장애가 발생하더라도 롤백 지점이 명확하게 분리되어 있다. 특히 분산 환경에서 가장 다루기 까다로운 **'로컬 DB 트랜잭션과 외부 API 통신 간의 타이밍 이슈'**를 완벽하게 제어할 수 있다. 만약 외부 API 호출 성공 직후 네트워크 단절로 자사 서버가 다운되더라도, Saga 오케스트레이터 패턴의 미완료 트랜잭션 로그를 기반으로 시스템 재기동 시 보상 트랜잭션을 안전하게 재시도할 수 있는 확장성을 갖추게 되었다.[8]
