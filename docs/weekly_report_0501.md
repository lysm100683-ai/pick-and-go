## 1. 요약

본 주차에는 Pick & Go 시스템의 **예약부(Reservation Sub-system)** 전체 파이프라인을 설계·구현하고, 그 첫 번째 단계인 **예약 검증부(Sub 1)**의 단위 검증을 완료하였다.

예약부는 사용자가 여행 일정을 선택한 뒤 항공권과 숙소를 자동으로 예약하는 핵심 기능으로, 총 5개의 서브시스템으로 구성된다. 이번 주에는 모든 서브시스템의 설계 및 코드 구현을 완료하였으며, 첫 번째 단계(예약 정보 유효성 검사)에 대해 8가지 시나리오·12개 항목의 자동화 검증 테스트를 수행하여 **전원 통과(Pass)**를 확인하였다.

> **핵심 성과**: 예약부 5단계 파이프라인 설계·구현 완료 / 예약 검증부 단위 테스트 100% 통과

## 2. 시스템 전체 구조

Pick & Go는 다음 5개 부서로 구성된다. 이번 주 작업은 **예약부**에 해당한다.

```
 ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐    ┌──────────┐
 │ 입력부 │ →  │  DB부 │ →  │ 처리부 │ →  │ 출력부 │ →  │  예약부  │
 └──────┘    └──────┘    └──────┘    └──────┘    └──────────┘
  사용자가     장소 정보    AI 기반      추천 일정     항공·숙소
  여행 조건    수집·저장    일정 생성     화면 표시     자동 예약
  입력
                                                  ↑ 이번 주 작업 범위
```

**각 부서 역할 요약**

| 부서 | 역할 | 개발 현황 |
|------|------|---------|
| 입력부 | 사용자 여행 조건 수집 (출발지, 날짜, 인원 등) | ✅ 완료 |
| DB부 | 장소·이동시간 데이터 수집 및 저장 | ✅ 완료 |
| 처리부 | AI 알고리즘으로 여행 일정 후보 생성 | ✅ 완료 |
| 출력부 | 추천 일정을 지도·카드 형태로 화면 표시 | ✅ 완료 |
| **예약부** | **선택된 일정의 항공·숙소 자동 예약** | **🔧 구현 중** |

## 3. 예약부 구조 설계

예약부는 사용자가 일정을 선택한 순간부터 예약 완료 알림까지의 전 과정을 담당한다.  
총 **5단계 파이프라인** 구조로 설계되었으며, 각 단계는 독립적으로 교체·테스트 가능하다.

### 3-1. 예약부 전체 흐름도

```
  [출력부에서 전달]
  선택된 여행 일정 + 사용자 정보 + 결제 수단
          │
          ▼
  ╔══════════════════════════════════════════╗
  ║  Sub 1  예약 검증부          ✅ 구현·테스트 완료  ║
  ║  예약 요청의 유효성을 사전 점검              ║
  ║  오류 발견 시 → 즉시 Sub 5로 이동            ║
  ╚══════════════════════════════════════════╝
          │ 검증 통과
          ▼
  ╔══════════════════════════════════════════╗
  ║  Sub 2  외부 예약 연동 관리부  🔧 구현 완료(모의)  ║
  ║  항공사·숙박업체 API를 동시에 호출하여 예약      ║
  ║  하나라도 실패 시 → 성공한 예약도 전부 취소      ║
  ╚══════════════════════════════════════════╝
          │ 모두 성공
          ▼
  ╔══════════════════════════════════════════╗
  ║  Sub 3  예약 확정 검증        🔧 구현 완료(모의)  ║
  ║  예약 번호 실존 여부 재확인 · 최종 금액 계산      ║
  ╚══════════════════════════════════════════╝
          │
          ▼
  ╔══════════════════════════════════════════╗
  ║  Sub 4  예약 정보 저장부      🔧 구현 완료(모의)  ║
  ║  예약 정보를 데이터베이스에 안전하게 기록         ║
  ║  저장 실패 시 → 자동 원복(Rollback)           ║
  ╚══════════════════════════════════════════╝
          │
          ▼
  ╔══════════════════════════════════════════╗
  ║  Sub 5  예약 결과 안내부      🔧 구현 완료(모의)  ║
  ║  성공: 예약 확인 + 이메일/SMS 발송             ║
  ║  실패: 실패 사유 안내 + 재시도 안내             ║
  ╚══════════════════════════════════════════╝
          │
          ▼
  [출력부로 반환]
  예약 완료 화면 또는 실패 안내 화면
```

### 3-2. 설계 핵심 원칙

| 원칙 | 적용 내용 | 근거 요구사항 |
|------|---------|------------|
| **일괄 예약** | 항공·숙소를 동시에 예약 시도 (하나라도 실패 시 전체 취소) | SRS M-11 |
| **15초 이내 완료** | 항공·숙소 병렬 동시 처리로 대기 시간 최소화 | SRS M-12 |
| **99.9% 성공률** | 예약 실패 이력 기록으로 품질 추적 | SRS M-13 |
| **알림 비동기 처리** | 이메일·SMS 발송을 응답과 분리하여 속도 보장 | SRS M-12 |
| **원자성 보장** | 데이터베이스 저장 실패 시 자동 원복 | DB ACID 원칙 |

## 4. 예약 검증부 상세 설계 (Sub 1)

예약 검증부는 파이프라인의 첫 번째 관문으로,  
잘못된 예약 요청이 시스템 안으로 들어오지 못하도록 사전 차단하는 역할을 한다.

### 4-1. 검증 흐름도

```
  [입력]
  여행 일정 데이터 · 사용자 ID · 출발지·목적지 · 인원 · 결제 수단
          │
          ▼
  ┌─────────────────────────────────────────┐
  │ ① 필수 정보 존재 확인                      │
  │    사용자 ID · 일정 데이터 · 도시 정보 누락 여부  │
  └─────────────────────────────────────────┘
          │
          ▼
  ┌─────────────────────────────────────────┐
  │ ② 날짜 유효성 확인                         │
  │    출발일 ≥ 오늘 · 종료일 > 출발일             │
  └─────────────────────────────────────────┘
          │
          ▼
  ┌─────────────────────────────────────────┐
  │ ③ 결제 수단 확인                           │
  │    허용된 결제 방식(카드·계좌이체)인지 확인       │
  └─────────────────────────────────────────┘
          │
          ▼
  ┌─────────────────────────────────────────┐
  │ ④ 중복 예약 확인                           │
  │    동일 날짜에 이미 예약된 내역이 있는지 조회       │
  └─────────────────────────────────────────┘
          │
          ▼
  ◇ 문제가 있는가?
    ├─ YES → 오류 코드 생성 → Sub 5 (결과 안내부)로 전달
    │         (사용자에게 구체적인 실패 사유 안내)
    └─ NO  → 검증 완료 패키지 생성 → Sub 2 (외부 예약 연동 관리부)로 전달

  [출력 - 성공] 검증 완료된 예약 정보 패키지
  [출력 - 실패] 오류 코드 + 사유 메시지 + 재시도 가능 여부
```

### 4-2. 오류 코드 정의

| 오류 코드 | 발생 조건 | 재시도 가능 |
|----------|---------|----------|
| `MISSING_USER_ID` | 사용자 정보 없음 | 불가 |
| `MISSING_TRIP_DATA` | 선택된 일정 없음 | 불가 |
| `MISSING_CITY` | 출발지 또는 목적지 없음 | 불가 |
| `INVALID_DATE_FORMAT` | 날짜 형식 오류 | 불가 |
| `PAST_DATE` | 출발일이 오늘 이전 | 불가 |
| `INVALID_DATE_RANGE` | 종료일이 출발일보다 이전 | 불가 |
| `INVALID_PEOPLE_COUNT` | 인원이 1명 미만 또는 8명 초과 | 불가 |
| `INVALID_PAYMENT_METHOD` | 허용되지 않은 결제 수단 | 불가 |
| `DUPLICATE_RESERVATION` | 동일 날짜 중복 예약 | 불가 |

## 5. 이번 주 구현 성과

### 5-1. 데이터베이스 설계 확장

예약 정보를 체계적으로 관리하기 위해 기존 단일 테이블을 **3개 테이블**로 분리 설계하였다.

| 테이블 | 저장 내용 | 역할 |
|--------|---------|------|
| `reservations` | 예약 ID · 사용자 · 상태 · 총 금액 | 예약 기본 정보 |
| `reservation_items` | 항공편 정보 · 숙소 정보 (각각 1행) | 예약 세부 항목 |
| `reservation_logs` | 성공·실패 이벤트 전체 이력 | 감사 추적(Audit Trail) |

> 이 구조는 향후 예약 현황 조회, 예약 취소·변경, 성공률 분석 등에 활용 가능하다.

### 5-2. 예약 API 교체

기존: 단순 응답 반환(껍데기 코드)
→ 이번 주: **실제 5단계 파이프라인 동작**으로 전면 교체

```
이전: POST /api/v1/reservation
      → 2초 대기 후 무조건 "예약 완료" 반환 (테스트용 더미 코드)

이후: POST /api/v1/reservation
      → Sub 1 검증 → Sub 2 병렬 예약 → Sub 3 확정 → Sub 4 저장 → Sub 5 응답
```

### 5-3. 모의(Mock) 방식 채택

실제 항공사(Amadeus)·숙박업체(Booking.com) API 계약 없이도  
전체 예약 흐름을 검증할 수 있도록 **모의 응답(Mock)** 방식으로 구현하였다.

| 구분 | 현재 방식 | 향후 전환 방식 |
|------|---------|------------|
| 항공 예약 | 모의 응답 (환경변수 `MOCK_FLIGHT=true`) | Amadeus API 연동 |
| 숙소 예약 | 모의 응답 (환경변수 `MOCK_HOTEL=true`) | Booking.com API 연동 |
| 이메일 발송 | 콘솔 출력으로 대체 | SMTP 실제 발송 |

## 부록. 기술 용어 설명

| 용어 | 설명 |
|------|------|
| **파이프라인** | 작업을 단계별로 순서대로 처리하는 구조. 공장의 컨베이어 벨트와 유사 |
| **모의(Mock) 구현** | 실제 외부 서비스 없이 가상의 응답으로 동작을 시뮬레이션하는 방식 |
| **병렬 처리** | 여러 작업(항공·숙소 예약)을 동시에 수행하여 처리 시간을 단축 |
| **롤백(Rollback)** | 오류 발생 시 이전 상태로 자동 복구하는 기능 |
| **트랜잭션** | 여러 데이터 저장 작업을 하나의 묶음으로 처리하여 부분 저장을 방지 |
| **비동기 처리** | 이메일·SMS 발송 등 시간이 걸리는 작업을 응답과 분리하여 처리 |
| **단위 테스트** | 개별 기능 하나하나를 독립적으로 검증하는 자동화 테스트 |
| **API** | 두 시스템이 데이터를 주고받을 때 사용하는 표준 통신 방식 |
| **ACID** | 데이터베이스 거래의 4가지 신뢰성 원칙 (원자성·일관성·격리성·영속성) |
