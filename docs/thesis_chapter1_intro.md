# 제 1 장 서론

## 1.1 연구 배경

스마트폰 보급과 온라인 여행 플랫폼의 성장으로 개인 맞춤형 여행에 대한 수요가 빠르게 증가하고 있다. 그러나 대부분의 여행자는 항공권 검색, 숙소 예약, 현지 관광지 탐색을 각각 별도의 서비스에서 수행해야 하며, 이를 통합하는 과정에서 상당한 시간과 노력이 소요된다.

본 논문은 이러한 문제를 해결하기 위해 설계된 통합 여행 자동화 서비스 **Pick & Go**를 주제로 한다. Pick & Go는 사용자가 출발지·목적지·여행 기간·여행 스타일 등 조건을 입력하면 AI가 맞춤 일정을 자동 생성하고 항공·숙소를 일괄 예약하는 엔드-투-엔드 시스템이다.

[그림 1]과 같이 Pick & Go는 다섯 개의 모듈로 구성된다.

**[표 1]** Pick & Go 시스템 주요 모듈 구성 및 역할

| 모듈 | 역할 |
|---|---|
| 사용자 입력부 | 여행 조건 수집 (출발지·목적지·기간·스타일 등) |
| 처리부 (AI 일정 생성) | 위치 기반 DB 조회 및 AI 최적화로 맞춤 일정 생성 |
| **DB부** | 장소 데이터 저장·이동시간 캐시 관리 ← **본 논문 담당** |
| **예약부** | 항공·숙소 5단계 자동 예약 파이프라인 ← **본 논문 담당** |
| 결과 출력부 | 완성된 일정·예약 결과 사용자 전달 |

> **[그림 1]** Pick & Go 전체 시스템 구성 개요도
> *(사용자 입력부 → 처리부(AI 일정 생성, PostGIS DB 조회) → 예약부(Sub1~Sub5 파이프라인) → 결과 출력부의 전체 데이터 흐름)*

본 논문은 전체 시스템 중 **DB부**와 **예약부** 두 서브시스템의 설계와 구현을 다룬다.

## 1.2 문제 정의

DB부와 예약부를 별도로 다루는 이유는 각 서브시스템이 독립적인 기술적 과제를 안고 있기 때문이다.

### 문제 1 — DB부: 대규모 위치 기반 데이터 탐색 성능

여행 일정 생성 과정에서 시스템은 수십만 건 이상의 장소·이동시간 데이터를 실시간으로 탐색해야 한다. 초기 구현에서 발생한 문제는 두 가지이다.

- **응답 시간 선형 증가**: 파일 기반 SQLite + 단순 좌표 수치 비교 방식은 데이터 건수에 비례(O(N))하여 탐색 시간이 늘어난다. 이동시간 캐시가 100만 건에 도달하면 1회 탐색에 약 55초가 소요되어 실시간 서비스가 불가능하다.[1]
- **반복 DB 접속 부하**: 외부 API로부터 수집된 장소 데이터를 건별로 즉시 저장하면, 수백 건 수집 시 수백 번의 DB 접속이 반복된다.

### 문제 2 — 예약부: 분산 예약의 데이터 일관성

항공권과 숙소를 각각 별개의 외부 API로 처리하는 방식에서는 부분 실패 시 데이터 불일치가 발생한다.

- **부분 성공 문제**: 항공 예약 성공 후 숙소 예약이 실패하면, 이미 확정된 항공 예약만 남아 사용자와 시스템 간 상태가 어긋난다.
- **수동 보상 처리 필요**: 자동화된 보상 체계가 없으면 서비스 운영 중 수동 개입이 빈번하게 발생한다.[2]

## 1.3 해결 방안 및 기여

본 논문에서 설계·구현한 두 가지 해결 방안을 요약하면 다음과 같다.

**[표 2]** DB부·예약부 서브시스템별 핵심 기술 및 설계 방안 비교

| | **DB부** | **예약부** |
|---|---|---|
| **핵심 기술** | PostGIS Geography 타입 + GiST 공간 인덱스 | Saga 패턴 + 보상 트랜잭션 |
| **탐색 함수** | `ST_DWithin` (인덱스 활용) | asyncio 비동기 병렬 호출 |
| **저장 구조** | 배치 Bulk Upsert + TTL 180일 자동 삭제 | 5단계 파이프라인 (Sub1~Sub5) |
| **성능/신뢰성** | 100만 건 기준 탐색 0.06초 이내 (추산) | 부분 실패 시 자동 보상·롤백 |

**DB부**에서는 PostgreSQL의 공간 확장 모듈 PostGIS를 활용하여 장소 좌표를 Geography 타입으로 저장하고, GiST 공간 인덱스를 적용한 `ST_DWithin` 반경 탐색으로 전환하였다. 벤치마크 측정 결과 1,533건 기준 응답 시간이 0.083초에서 0.063초로 약 30% 개선되었으며, 데이터 규모가 100만 건으로 증가해도 로그적 수준으로 수렴할 것으로 추산된다.[3]

**예약부**에서는 항공(Amadeus)·숙소(Booking.com) API를 비동기 동시 호출하여 처리 속도를 단축하고, 부분 실패 시 Saga 패턴의 보상 트랜잭션을 통해 이미 성공한 예약을 자동 취소함으로써 데이터 불일치를 원천 차단한다.[4]

## 1.4 논문 구성

본 논문은 다음과 같이 구성된다.

| 장 | 제목 | 내용 |
|---|---|---|
| 제2장 | 배경 기술 | PostGIS·GiST 인덱스, Saga 패턴 개념 |
| 제3장 | 이동시간 캐시 DB 설계 | 스키마·GiST 인덱스·TTL 정책·중복 방지 |
| 제4장 | GiST 인덱스 탐색 최적화 | ST_Distance → ST_DWithin 전환 설계 |
| 제5장 | 배치 기반 장소 데이터 수집 | Bulk Upsert 저장 구조 |
| 제6장 | 예약 파이프라인 설계 | Sub1~Sub5 5단계 흐름 및 보상 트랜잭션 |
| 제7장 | 예약 DB 스키마 설계 | 예약·결제·취소 테이블 구조 |
| 제8장 | 구현 검증 결과 | 예약 검증부(Sub 1) 단위 테스트 |
| 제9장 | 결론 및 향후 연구 | 성과 요약·개선 방향 |
