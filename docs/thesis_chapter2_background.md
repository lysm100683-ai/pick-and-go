# 제 2 장 배경 기술

본 장에서는 Pick & Go 시스템의 DB부와 예약부 구현에 사용된 세 가지 핵심 기술—PostGIS 공간 데이터베이스, GiST 공간 인덱스, Saga 패턴—의 개념과 본 시스템에서의 적용 방식을 기술한다.

---

## 2.1 공간 데이터베이스와 PostGIS

### 공간 데이터베이스의 필요성

일반 관계형 데이터베이스(RDBMS)는 숫자·문자 데이터를 효과적으로 관리하지만, 위도·경도 좌표와 같은 **공간 데이터(spatial data)**를 기본적으로 지원하지 않는다. 공간 데이터 처리에는 단순 산술 연산과 다른 기하학적 연산이 필요하다.

- **거리 계산**: 두 좌표 사이의 지표면 실제 거리 (지구 곡률 반영 필요)
- **반경 탐색**: 기준점에서 반경 r 이내에 있는 모든 객체 조회
- **포함 판단**: 특정 좌표가 어떤 영역(다각형) 내에 위치하는지 판별

이를 지원하는 데이터베이스를 **공간 데이터베이스(Spatial Database)**라 하며, 본 시스템에서는 PostgreSQL의 공간 확장 모듈인 **PostGIS**를 채택하였다.[3][6]

### PostGIS Geography 타입

PostGIS는 OGC(Open Geospatial Consortium) 표준을 준수하며, 좌표를 저장하는 타입으로 **Geography**와 Geometry 두 가지를 제공한다. 본 시스템에서는 지구 곡률을 반영한 정확한 미터 단위 거리 계산이 필요하므로 **Geography(POINT, 4326)** 타입을 채택하였다.

**[표 3]** PostGIS Geometry 타입과 Geography 타입의 특성 비교

| 구분 | Geometry 타입 | **Geography 타입** (채택) |
|---|---|---|
| 좌표 기준 | 평면 투영 좌표계 | **WGS84(EPSG:4326) 구면 좌표계** |
| 거리 계산 | 평면 유클리드 거리 | **지구 곡률 반영 실제 거리 (미터)** |
| 고위도 정확도 | 오차 발생 가능 | 정확 |
| 적합 용도 | 소규모 지역 내 계산 | 국가·대륙 단위 거리 계산 |

장소의 위치는 `POINT(경도 위도)` 형식의 공간 객체로 저장되며, 본 시스템의 `places` 테이블과 `movement_cache` 테이블 좌표 컬럼에 적용하였다.

[그림 2]는 WGS84 좌표계에서 두 공간 함수의 동작 차이를 나타낸 개념도이다. 서울(POINT A)과 부산(POINT B) 사이의 대권 경로(약 325 km)를 `ST_Distance`가 반환하는 과정과, 기준점 A로부터 반경 50m 이내를 `ST_DWithin`이 판별하는 과정을 비교한다.

> **[그림 2]** WGS84 좌표계에서의 POINT 객체와 ST_Distance·ST_DWithin 탐색 범위 비교
> *(좌) 지구 구면 위의 POINT A(서울)·POINT B(부산) 표현 및 대권 경로(약 325 km)*
> *(우) ST_Distance는 전체 N개 레코드 순차 비교 / ST_DWithin은 반경 r 밖 영역 일괄 제외 후 후보군만 정밀 비교하는 방식 도식*

## 2.2 GiST 공간 인덱스와 반경 탐색

### 인덱스 유형 비교

인덱스(Index)가 없으면 데이터베이스는 조건에 맞는 레코드를 찾기 위해 전체 행을 순차 비교하는 **풀 스캔(Full Scan)**을 수행한다. PostgreSQL에서 일반적으로 사용되는 B-Tree 인덱스는 좌표 데이터에 적용할 수 없으며, 공간 데이터 탐색에는 **GiST(Generalized Search Tree)** 인덱스가 필요하다.[1]

**[표 4]** B-Tree 인덱스와 GiST 인덱스의 특성 비교

| 구분 | B-Tree 인덱스 | **GiST 인덱스** (채택) |
|---|---|---|
| 탐색 방식 | 숫자·문자 대소 비교 | **경계 상자(Bounding Box) 계층 구조** |
| 공간 데이터 지원 | 불가 | **가능** |
| 반경 탐색 복잡도 | O(N) 풀 스캔 | **O(log N) 계층 제외** |
| 적용 함수 | `=`, `<`, `>` 등 | `ST_DWithin`, `ST_Intersects` 등 |

GiST 인덱스는 공간 객체를 계층적 경계 상자 트리로 구조화하여, 탐색 반경 밖에 있는 전체 영역을 한 번에 제외한다. 이로써 수백만 건의 데이터에서도 실제 비교 대상을 수 건~수십 건으로 좁혀 응답 시간을 일정 수준으로 유지한다.

[그림 3]은 풀 스캔 방식과 GiST 인덱스 방식의 동작 원리를 비교한 도식이다.

> **[그림 3]** GiST 인덱스 구조와 반경 탐색 동작 원리 비교
> *(좌) 풀 스캔: 전체 N개 레코드를 순차 비교하는 방식 도식*
> *(우) GiST + ST_DWithin: 경계 상자 계층 구조에서 반경 외 영역을 일괄 제외하고 후보군만 정밀 비교하는 방식 도식*

### ST_Distance vs ST_DWithin

PostGIS에서 반경 탐색에 사용되는 두 함수의 차이는 다음과 같다.[1][5]

**[표 5]** ST_Distance 함수와 ST_DWithin 함수의 성능 비교

| 구분 | `ST_Distance(a, b)` | **`ST_DWithin(a, b, r)`** (채택) |
|---|---|---|
| 반환값 | 두 점 간 거리(미터) | 반경 r 이내 여부(Boolean) |
| 인덱스 활용 | ❌ 인덱스 미활용 → 풀 스캔 | ✅ GiST 인덱스 활용 |
| 탐색 복잡도 | O(N) | O(log N) |
| 1,533건 응답 시간 | 0.083초 | **0.063초 (약 30% 개선)** |
| 100만 건 추산 | 약 55초 (실시간 불가) | **0.06초 이내** |

본 시스템의 이동시간 캐시 탐색에서는 `ST_Distance` 방식을 `ST_DWithin` + GiST 인덱스 방식으로 전환하였으며, 상세 벤치마크 결과는 제5장에서 기술한다.

[그림 4]는 두 방식의 데이터 건수별 응답 시간 추이를 비교한 그래프이다.

> **[그림 4]** ST_Distance vs ST_DWithin + GiST 데이터 건수별 응답 시간 비교 그래프
> *(x축: 데이터 건수 (1천~100만), y축: 응답 시간(초). ST_Distance는 선형 증가 직선, ST_DWithin + GiST는 완만한 곡선으로 수렴하는 형태)*

## 2.3 Saga 패턴과 보상 트랜잭션

### 분산 트랜잭션 문제

Pick & Go 예약부는 항공(Amadeus API)과 숙소(Booking.com API)를 각각 독립된 외부 서비스로 처리한다. 두 예약이 단일 데이터베이스 트랜잭션으로 묶이지 않으므로, 항공 예약 성공 후 숙소 예약이 실패하면 **부분 성공 상태**가 발생한다.

전통적인 해결책인 **2단계 커밋(2-Phase Commit, 2PC)**은 각 서비스가 트랜잭션 완료를 기다리는 동안 자원을 점유하여 성능 저하와 교착 상태(deadlock)를 유발할 수 있어 마이크로서비스 환경에 적합하지 않다.[2]

**[표 6]** 2단계 커밋(2PC)과 Saga 패턴의 특성 비교

| 구분 | 2단계 커밋(2PC) | **Saga 패턴** (채택) |
|---|---|---|
| 트랜잭션 방식 | 전체 잠금 후 일괄 커밋 | **단계별 독립 로컬 트랜잭션** |
| 실패 처리 | 전체 롤백 | **보상 트랜잭션 개별 실행** |
| 외부 API 연동 | 불가 (트랜잭션 경계 초과) | **가능** |
| 성능 | 잠금 대기로 인한 저하 | **비동기 병렬 처리 가능** |

### Saga 패턴 개념

Saga 패턴은 복합 트랜잭션을 여러 개의 독립적인 로컬 트랜잭션으로 분리하고, 중간에 실패가 발생하면 이미 완료된 단계를 되돌리는 **보상 트랜잭션(Compensating Transaction)**을 실행하여 원자성을 보장한다.[4]

[그림 5]는 예약부 Saga 패턴의 정상 흐름과 실패 시 보상 트랜잭션 발동 흐름을 나타낸다.

- **정상 흐름**: Sub1(검증) → Sub2(항공·숙소 병렬 예약 성공) → Sub3(확정) → Sub4(DB 저장) → Sub5(성공 응답)
- **실패 흐름**: Sub2 항공 성공 → 숙소 실패 → 보상 트랜잭션 발동 → **항공 예약 자동 취소** → Sub5(실패 응답)

> **[그림 5]** Saga 패턴 기반 예약 파이프라인 정상 흐름 및 실패 시 보상 트랜잭션 흐름도

본 시스템의 Sub2(외부 예약 연동 관리부)에서는 항공·숙소 API를 `asyncio.gather`로 비동기 동시 호출하고, 하나라도 실패할 경우 즉시 취소 API를 호출하여 원상 복구한다. 상세 구현은 제6장에서 기술한다.
